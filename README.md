# Folio — Transaction Ledger API

A transaction-ledger backend (accounts, credits, debits, history, transfers) built with
**Node.js + Express + SQLite**, plus a light "paper ledger" web UI served by the same server.

> Full Stack Developer Assessment — *Transaction Ledger API*

| | |
|---|---|
| **Backend** | Node.js (≥ 18), Express 4 |
| **Database** | SQLite via `better-sqlite3` (single file, zero setup) |
| **Tests** | Node's built-in test runner (`node:test`) — **61 tests**, no extra test deps |
| **UI** | Vanilla HTML/CSS/JS at `http://localhost:3000` |

---

## 🚀 Quick start

```bash
# 1. unzip, then
cd transaction-ledger-api

# 2. install dependencies
npm install

# 3. (optional) load demo data so the UI isn't empty
npm run seed

# 4. start the server
npm start
```

Open **http://localhost:3000** for the UI. The API lives under **http://localhost:3000/api**.

| Command | What it does |
|---|---|
| `npm start` | Start the server (port `3000`) |
| `npm run dev` | Start with auto-restart on file changes |
| `npm test` | Run the full test suite (uses an in-memory DB, never touches your data) |
| `npm run seed` | Add 3 demo accounts with sample transactions |

**Configuration (environment variables)**

| Variable | Default | Meaning |
|---|---|---|
| `PORT` | `3000` | HTTP port |
| `DB_PATH` | `./data/ledger.db` | SQLite file location |

e.g. `PORT=4000 DB_PATH=/tmp/my.db npm start` (Windows PowerShell: `$env:PORT=4000; npm start`).

> **Requirements:** Node.js 18 or newer. `better-sqlite3` ships prebuilt binaries for current Node
> versions, so `npm install` normally needs no compiler. If it ever tries to compile from source,
> install your platform's build tools (Windows: "Desktop development with C++"; macOS: `xcode-select --install`).

## 🧪 Try it in 60 seconds (curl)

```bash
# create two accounts
A=$(curl -s -X POST localhost:3000/api/accounts -H 'Content-Type: application/json' -d '{"name":"Alice"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).id')
B=$(curl -s -X POST localhost:3000/api/accounts -H 'Content-Type: application/json' -d '{"name":"Bob"}'   | node -pe 'JSON.parse(require("fs").readFileSync(0)).id')

# credit 100 to Alice
curl -s -X POST localhost:3000/api/accounts/$A/transactions -H 'Content-Type: application/json' \
  -d '{"type":"credit","amount":100,"reference_id":"INV-1","description":"Opening deposit"}'

# same reference again -> 409, balance unchanged
curl -s -X POST localhost:3000/api/accounts/$A/transactions -H 'Content-Type: application/json' \
  -d '{"type":"credit","amount":100,"reference_id":"INV-1"}'

# debit more than the balance -> 422
curl -s -X POST localhost:3000/api/accounts/$A/transactions -H 'Content-Type: application/json' \
  -d '{"type":"debit","amount":150,"reference_id":"D-1"}'

# transfer 30 from Alice to Bob
curl -s -X POST localhost:3000/api/transfers -H 'Content-Type: application/json' \
  -d "{\"from_account_id\":\"$A\",\"to_account_id\":\"$B\",\"amount\":30,\"reference_id\":\"T-1\"}"

# balance + history (latest first, paginated, filterable)
curl -s localhost:3000/api/accounts/$A/balance
curl -s "localhost:3000/api/accounts/$A/transactions?type=debit&page=1&limit=5"
```

## 🛡 How data integrity is guaranteed

Requirements from the brief → how they are enforced:

| Requirement | Enforcement |
|---|---|
| Initial balance always 0, client can't set it | Account insert hard-codes `0`; a `balance` field in the request is rejected with `400` |
| `id`, `created_at` generated by the system | UUID + ISO timestamp created server-side; client-supplied values are rejected |
| Credit/debit change the balance correctly | Single code path (`applyTransaction`) in `ledger.js` |
| Reject debit when balance is insufficient | Checked in the service **and** `CHECK (balance >= 0)` in the DB |
| Duplicate `reference_id` per account | Pre-check → `409` with the original transaction **and** `UNIQUE (account_id, reference_id)` constraint as a race-proof safety net. Same reference on *different* accounts is fine |
| Transactions immutable | No update/delete routes (`405`), **and** DB triggers abort any `UPDATE`/`DELETE` on `transactions` |
| Balance = result of all valid transactions | Each row stores `balance_after`; `GET /api/accounts/:id/verify` recomputes the balance from the log and compares |
| Rejected/failed ops never touch the balance | Everything runs in a `BEGIN IMMEDIATE` transaction; any throw rolls back |
| Atomic "create transaction + update balance" | Same DB transaction (proved by a test that forces the balance update to fail) |
| Atomic transfer, never partial | Debit + credit + transfer record in one DB transaction (proved by tests that fail the credit leg) |
| Money precision | Stored as **integer paise**; API accepts ≤ 2 decimal places (`0.1 + 0.2 = 0.30` exactly) |
| Concurrency | SQLite serialises writers; tested with 20 parallel debits and 10 parallel duplicate requests |

## ✅ Test coverage

`npm test` runs 61 HTTP-level tests covering every section of the brief: account creation rules,
credit/debit maths (including the exact examples from the PDF), insufficient funds, duplicates
(incl. parallel), balance endpoint, history filtering / pagination / ordering, immutability (API and
database level), balance consistency, atomicity/rollback, validation, error format, and transfers
(including rollback of a half-completed transfer and opposite parallel transfers).

## 🎨 The UI

*Folio* is styled as a paper accounting ledger: ruled pages with a red margin, index-tab accounts,
debit/credit columns with a running balance, a "Books balanced" seal driven by the `/verify`
endpoint, and rubber-stamp notifications for rejected or duplicate entries. Light theme, responsive.
